# Open Audio recommendations for M14U

Checked 2026-11-26. Start with a web-only, metadata-based “More like this” shelf. Prefer real Audius relationships when available, supplement them with metadata, and fall back to clearly labeled discovery. Do not use audio downloads or embeddings as a launch dependency. Hold Free To Use out of new in-app playback recommendations until its permitted use is confirmed.

## What the repo does today

- [HomePage](../src/pages/HomePage.tsx) computes a recent-history seed, but the Open Audio branch calls `getOpenAudioFeatured()` without it. [Home discovery](../src/services/homeDiscovery.ts) requests `/api/search-discovery` and falls back to static tracks. The [Worker](../src/backend/worker.ts) returns three fixed picks via `featuredOpen`; `/api/up-next` accepts only YouTube IDs. `/api/similar` uses title and artist with optional Last.fm configuration; it is not an Open Audio ID-to-ID graph. Android uses its existing YouTube recommendations and native playback. Leave both Android and JioSaavn behavior unchanged.
- [Open Audio adapters](../src/backend/openCatalog.ts) round-robin the providers on search, hide media URLs in search results, and revalidate provider-qualified IDs in `/api/stream`. They leave `authorId` empty and do not retain usable genre or tags in normalized results. Recommendations need richer internal metadata, not changes to the queue or a media proxy. A static fallback is not evidence of current rights or availability. See [previous playback probes](open-music-api-research.md).

## Provider signals and limits

### Audius: strongest documented seed relationships

The [official OpenAPI source](https://github.com/AudiusProject/audius-protocol/blob/main/packages/docs/docs/public/openapi.yaml) documents `GET /tracks/{track_id}/remixes` (children) and `/tracks/{track_id}/remixing` (parents). These are track relationships, not proof of acoustic similarity; many seeds may have neither. For a second tier, use the uploader ID from the seed and `/users/{id}/tracks`; `/users/{id}/related` returns artist/user suggestions, not tracks. Related users are a weaker discovery signal and expanding all their track lists would multiply requests. `/users/{id}/recommended-tracks` is scoped to an Audius user, not an M14U seed; `/tracks/recommended` accepts genre, time, user and exclusion inputs but no seed track input. Trending by genre is a discovery fallback, not “related to this track.” No general seed-track similarity route was found in the spec.

Retain Audius genre, mood, tags, uploader ID and remix provenance alongside the current access checks (`is_streamable`, `access.stream`, accepted license label and canonical permalink). Run the same checks on candidates from any relationship endpoint. Treat the license label as incomplete for reuse because the current adapter does not have an exact CC version. Use the [Audius terms](https://audius.co/legal/terms-of-use), track page and API access/download fields to check the proposed use separately from streaming. Anonymous read is represented in the spec, not guaranteed at runtime: detail, remixes and trending returned `403` from this research environment. That does not establish a provider outage or endpoint removal; verify representative open-license seeds from the deployed environment before depending on them.

### Openverse–Jamendo: metadata discovery, not a relationship API

The [Openverse API reference](https://docs.openverse.org/api/reference/) exposes audio search/detail and indexing metadata (creator, title, source, category, license, duration, tags where available, canonical landing page); no seed relationship appears in that interface. Use provider-scoped creator/title/tag search as candidate generation and re-rank locally; a query hit is not an exact artist match. Keep the existing Jamendo source, approved license and full-track URL guards. Openverse is an index, not the rights holder or media host. Its [terms](https://docs.openverse.org/terms_of_service.html) and [throttling docs](https://docs.openverse.org/api/reference/authentication_and_throttling.html) matter separately from Jamendo's terms and the track license. The featured detail request returned `403` from this environment; previous repo probes found playable byte ranges but no CORS on one Jamendo asset. Neither observation establishes general availability.

If keyed enrichment is justified, use the Jamendo ID from the already-validated Jamendo landing page, not the Openverse UUID. Jamendo's [tracks API](https://developer.jamendo.com/v3.0/tracks) supports artist filtering, `include=musicinfo`, tags/fuzzy tags, speed, acoustic/electric and vocal/instrumental filters. `xartist` is a search for music similar to a named **non-Jamendo** artist, not a seed-track endpoint. [Charts](https://developer.jamendo.com/v3.0/charts/track) are discovery, not an acoustic neighbor list. [App authentication](https://developer.jamendo.com/v3.0/authentication#authentication-app) requires a registered `client_id`. The [API terms](https://devportal.jamendo.com/api_terms_of_use) cover commercial approval, attribution/backlinks, caching only as reasonably necessary, and no app designed for offline content access. The API distinguishes streaming and `audiodownload_allowed`; do not treat an Openverse media URL as a workaround for a download flag or as permission to build a local corpus.

### Free To Use: metadata exists; permission and API stability do not follow

The [first-party detail endpoint](https://api.freetouse.com/v3/music/tracks/db409ac0-930a-4f4f-bff3-a63278673a6f) used by the repo returned `200` for “Adored,” with `genre: Hip Hop/Rap`, artist records, categories and `[id, label]` tag tuples including `trumpet`, `smooth` and `warm`. This is one observed response; no public recommendation edge or stable API contract was verified. These would be useful metadata signals only if the integration is authorized. The [current license](https://freetouse.com/license) grants free use of non-premium assets in qualifying user-generated social content with attribution (monetization there can be allowed); it is not a blanket noncommercial license. Section 3 prohibits making assets available to third parties and using them to train, fine-tune or otherwise develop AI/ML models. Neither a direct MP3 nor the repo's “Free To Use (noncommercial)” label establishes permission for an in-app jukebox. Ask for written clarification on API access, direct playback, metadata retention and fixed-model inference separately. Exclude these recordings from embedding work absent express permission, and review the existing integration independently of this feature.

## Suggested first version

1. Resolve a supported Open Audio seed by its source-qualified ID. Keep recommendation lookup separate from YouTube `/api/up-next`. Use one bounded native lookup when applicable, then bounded artist/tag/genre retrieval if results are thin. Start with recent history or an explicit track action; no history should show curated discovery without suggesting personalization. Never send a user's complete history upstream.
2. Normalize metadata internally: provider and source ID, canonical URL, artist display name and provider artist ID, title, optional genre/mood/tags/duration, optional relation type and provenance, access flags, license label and exact URL when verified. Prefer native relationship evidence, then same-provider artist ID plus compatible tags, then specific shared tags/mood/genre. Use duration only as a weak tie-breaker; no title-only similarity or inferred language. Keep provider terms and rankings interpretable; show “Remix,” “Same artist” or “Shared tags” only when that evidence exists. Do not merge different recordings on title/artist alone.
3. Drop the seed and duplicate IDs, limit repeated artists, and reserve space for cross-provider matches only when they score well. A provider-wide popularity list or curated fallback belongs under “Discover,” not “More like this.” Follow the existing [provider budget](../src/backend/providerBudget.ts) and partial-failure model; use short-lived metadata caches within provider rules and never cache media bytes or signed redirects. Recheck on playback and fail gracefully when a candidate is removed, gated, or no longer licensed. Do not auto-enqueue from an untested recommendation shelf.
4. Validate with a small fixed seed set: a known Audius remix pair, an Audius seed with no edges, Jamendo details with and without useful tags, an unsupported/legacy seed, and upstream timeouts/403/429. Compare top-five relevance and playable coverage against curated discovery, checking duplicates, artist concentration, empty states and p95 lookup latency. Confirm open-track license filters, metadata-only responses and actual browser startup/seek; keep Android's existing YouTube path in regression coverage. No end-to-end playback or recommendation quality was measured here.

## Offline audio similarity: a later experiment

Use a small corpus of own recordings, explicitly permissioned tracks, or verified CC0 material as the initial baseline. Keep provenance for the recording **and** underlying work; do not infer rights from artwork, labels or index entries. Compare a non-learned tempo/timbre feature baseline with frozen [Discogs-EffNet or MSD-MusiCNN embeddings](https://essentia.upf.edu/models.html#feature-extractors). The [Essentia extraction tutorial](https://essentia.upf.edu/tutorial_tensorflow_auto-tagging_classification_embeddings.html) documents frame embeddings; standardize model input, sample multiple track sections, pool and normalize vectors, and evaluate cosine nearest neighbors against the metadata baseline with blinded listening. A model learns the distinctions in its training objective; acoustic similarity need not imply listener preference. Precompute offline rather than decoding audio in the Worker or user browser. Consider publishing only reviewed neighbor IDs, not media or vectors, after confirming output rights.

Check four permissions independently: obtaining/temporarily copying audio; analyzing it for the intended purpose; retaining or sharing features and neighbors; and deploying the extractor and weights. [Essentia licensing](https://essentia.upf.edu/licensing_information.html) separates the AGPL/proprietary software from MTG's CC BY-NC-SA 4.0/proprietary weights. Check the exact checkpoint, deployment and outputs rather than assuming that frozen inference makes licensing irrelevant. [CC BY](https://creativecommons.org/licenses/by/4.0/) and [CC BY-SA](https://creativecommons.org/licenses/by-sa/4.0/) require attention to attribution and, for shared adapted material under BY-SA, compatible licensing; verify each actual version and whether the proposed output is adapted material instead of assuming all vectors are unrestricted or necessarily adaptations. [Public Domain Mark](https://creativecommons.org/publicdomain/mark/1.0/) is a label, not a grant like [CC0](https://creativecommons.org/publicdomain/zero/1.0/). Platform access terms and third-party rights still matter. Log source and rights evidence, media fingerprint or revision, model version, and removal/rebuild policy. Do not bulk-ingest any of the three production providers without permission for the specific processing and retention plan.
