# Invidious provider review — 2026-11-24

**Do not ship the ChocolateMoo hostnames as a drop-in default yet.** From one test network, both public APIs returned metadata for `dQw4w9WgXcQ` and `3JZ_D3ELwOQ`, but both returned HTTP 500 for `jfKfPfyJRdk`. With `Origin: https://example.org`, both returned `Access-Control-Allow-Origin: *` on the first video's metadata. Reproducing M14U's origin rewrite for selected itag 251 and requesting `Range: bytes=0-1023` produced 403 for the rewritten `/videoplayback` URLs and HTML instead of audio for the EU host's rewritten `/companion/sabr-segment`. Direct CDN requests sometimes returned 206 audio, which does not establish browser playback or instance proxy support. `local=true` also failed for the first video on both hosts in this snapshot. These checks do not identify the serving proxy implementation or invalidate earlier successes on other tracks/networks.

## Code implications

- [`getStreamData.ts`](../src/lib/modules/getStreamData.ts) prioritizes build-time `VITE_INVIDIOUS_URL`, then saved Zustand state, then the first default. A saved retired host incurs a first-attempt delay; prefetch returns early rather than trying the fallback pool. Normalize and migrate saved defaults without deleting deliberate custom configuration.
- [`helpers.ts`](../src/lib/utils/helpers.ts) has a duplicate list used only by `audioProxyHandler`, with no current call sites in `src`. Actual playback uses `proxyHandler` in [`playerStore.ts`](../src/stores/playerStore.ts) and rewrites the origin of an absolute URL; this breaks separate Companion hosts and throws for relative URLs. Preserve provider-issued media URLs where valid and normalize relative URLs against the issuing provider. Avoid rewriting arbitrary media paths/hosts.
- The current fallback stops at metadata success, not playback success. A bad media URL can be cached for five minutes. Retry on actual media failure, invalidate failed stream entries, and test the chosen audio itags, startup, seek/resume, content type and nonzero byte ranges in real browsers from the deployed origin. Native resolution precedes this web fallback.

## Alternatives

- Prefer a validated, operator-controlled deployment of [Invidious and its official Companion](https://github.com/iv-org/invidious-companion), using `VITE_INVIDIOUS_URL`. [ytproxy-go](https://git.nadeko.net/Fijxu/ytproxy-go) is a separate media proxy, not a substitute for extraction or a guarantee of reliable upstream access. Use [the Invidious API docs](https://docs.invidious.io/api/) and [official instance guidance](https://docs.invidious.io/instances/) to distinguish API support and instance availability from playback.
- A Worker playback route using the existing [YouTube.js](https://github.com/LuanRT/YouTube.js) dependency is a prototype option. Metadata support today does not establish media playback from deployed Cloudflare egress; test upstream session/token/URL expiration behavior, media delivery, and [Worker limits](https://developers.cloudflare.com/workers/platform/limits/) before committing.
- [Piped's schema](https://github.com/TeamPiped/OpenAPI) uses `/streams/{videoId}` with `audioStreams`, not Invidious `adaptiveFormats`. It needs an adapter and playback checks; throttling is a deployment-specific observation, not a schema property.

Present the original instance survey as point-in-time evidence: report timeout/403/503 as observed, not proof of permanent closure, a specific blocking mechanism, or the cause of failures across most public instances. Public instances should be opt-in until verified for playback, not represented as durable infrastructure.
