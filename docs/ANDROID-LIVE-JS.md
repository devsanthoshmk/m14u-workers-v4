# Android WebView live JavaScript updates

**Recommendation:** Keep the Android release booting from bundled web assets and use Play releases for changes to the native shell. Deploy backend fixes independently where the app already calls the Worker. If installed clients need web-code hotfixes, evaluate a signed, versioned web-bundle updater separately; do not turn on the dev server URL in production.

## What can change without a new Android build?

- **Development live reload:** Capacitor can point the WebView at a reachable Vite dev server and reload web changes without rebuilding the native binary. Capacitor explicitly marks `server.url`, `server.cleartext`, and `server.allowNavigation` as not intended for production. The commented `server.url` example in this repo is not a release recommendation. [Capacitor live reload](https://capacitorjs.com/docs/guides/live-reload) · [Configuration schema](https://capacitorjs.com/docs/config#schema) · [Repo config](../capacitor.config.ts)
- **Packaged web assets:** This project's `webDir` is `dist`. The usual build and `npx cap sync android` copy the output into the Android project; already installed copies do not pick up a Pages deploy. The current native [AppUpdater](../android/app/src/main/java/dev/m14u/app/AppUpdater.kt) checks GitHub releases for APK updates, not web bundles. [Capacitor development workflow](https://capacitorjs.com/docs/basics/workflow)
- **Production web-bundle updates:** Capacitor documents live deployment and its Android bridge can serve a different local directory (`setServerBasePath`) or return to packaged assets (`setServerAssetPath`). Those methods reload the app; they do not implement download, verification, or rollback. Only web assets compatible with the installed shell can change this way. A Kotlin/Java plugin, NewPipeExtractor dependency, new native permission, or native bridge API change needs a new native release. [Capacitor deployment guide](https://capacitorjs.com/docs/guides/deploying-updates#deploy-realtime-updates-with-appflow) · [Capacitor 8.3.0 Android source](https://github.com/ionic-team/capacitor/blob/8.3.0/android/capacitor/src/main/java/com/getcapacitor/Bridge.java#L1406-L1434)

## Android security and Google Play policy

Google Play prohibits apps distributed through Play from updating themselves outside Play's update mechanism or downloading executable code such as DEX, JAR, or `.so` files from elsewhere. The policy expressly excepts code running in an interpreter or VM that provides indirect access to Android APIs, such as WebView JavaScript. Runtime-loaded interpreted code still must not allow policy violations; the exception is not blanket approval for a particular Capacitor bridge, update system, or app feature. Do not offer the GitHub APK update path in a Play build; use Play's update mechanism instead. [Play Device and Network Abuse policy, Full Policy](https://support.google.com/googleplay/android-developer/answer/9888379?hl=en) · [Play in-app updates](https://developer.android.com/guide/playcore/in-app-updates)

A WebView with a native bridge is a privileged surface. Android recommends trusted content, HTTPS, explicit origin/host checks, and not exposing native interfaces to untrusted content. Play lists loading untrusted content or unverified URLs in a WebView with an added JavaScript interface as a violation example. HTTPS is necessary for transport, not a substitute for trusting the code or limiting what it can call. [Android WebView bridge risks](https://developer.android.com/privacy-and-security/risks/insecure-webview-native-bridges) · [Play policy](https://support.google.com/googleplay/android-developer/answer/9888379?hl=en)

If we adopt an updater, keep the bundled build as the offline fallback. Ship whole web bundles over HTTPS, verify a signed manifest and bundle integrity before activation, stage in app-private storage, and select bundles only for compatible native versions. Activate atomically, retain a known-good version, and roll back on startup failure. Test first launch offline, invalid signatures, incomplete downloads, crashes during activation, and old shells. These are release safeguards, not Play approval. [Android dynamic code loading guidance](https://developer.android.com/privacy-and-security/risks/dynamic-code-loading)

## Running `youtubei.js` inside the WebView

- **Use the browser entry, not the Worker build.** The [lockfile](../pnpm-lock.yaml) resolves `youtubei.js` to `16.0.1`, and the [backend](../src/backend/utils.ts) currently imports it server-side. For a WebView experiment, `youtubei.js/web` explicitly selects the browser implementation; `youtubei.js/web.bundle` is the prebuilt browser bundle. The bare import depends on the bundler's export conditions. The web implementation defaults to `globalThis.fetch`. [v16.0.1 package exports](https://github.com/LuanRT/YouTube.js/blob/v16.0.1/package.json#L29-L61) · [Web platform shim](https://github.com/LuanRT/YouTube.js/blob/v16.0.1/src/platform/web.ts#L93-L115)
- **A browser build does not remove CORS.** Upstream's [browser example README](https://github.com/LuanRT/YouTube.js/blob/v16.0.1/examples/browser/README.md) calls for a server-side proxy and marks the demo outdated. The library sets `credentials: 'include'` for browser API requests; a cross-origin response must allow the specific origin and credentials, not `*`. Neither bundling the library inside the APK nor successfully playing a media URL proves the WebView can read a cross-origin API response. [HTTP client](https://github.com/LuanRT/YouTube.js/blob/v16.0.1/src/utils/HTTPClient.ts#L139-L149) · [Fetch standard](https://fetch.spec.whatwg.org/#cors-protocol-and-credentials)
- **A custom transport must behave like Fetch.** `Innertube.create({ fetch })` accepts a Fetch-compatible override. Player bootstrap uses URL inputs; API calls pass a `Request` with a separate `init` containing the final headers and body. Test both paths and the `Response` operations used by each feature. Capacitor HTTP can route requests through native libraries and optionally patch global `fetch`/XHR, but that is a separate transport choice, not a guarantee of library compatibility. Prefer the existing Worker API to exposing an arbitrary forwarding endpoint or native HTTP bridge. [Fetch override type](https://github.com/LuanRT/YouTube.js/blob/v16.0.1/src/types/PlatformShim.ts#L4-L6) · [Player bootstrap](https://github.com/LuanRT/YouTube.js/blob/v16.0.1/src/core/Player.ts#L42-L84) · [HTTP client](https://github.com/LuanRT/YouTube.js/blob/v16.0.1/src/utils/HTTPClient.ts#L139-L149) · [Capacitor HTTP](https://capacitorjs.com/docs/apis/http)
- **Startup flags do not fix later requests.** `generate_session_locally: true` skips server session-data retrieval, but `retrieve_innertube_config` is separate and defaults to on. Setting `retrieve_innertube_config: false` skips config retrieval; `retrieve_player: false` skips player bootstrap and is not appropriate for features that need player processing. None of these changes CORS for later API calls. [Session creation](https://github.com/LuanRT/YouTube.js/blob/v16.0.1/src/core/Session.ts#L301-L326) · [Defaults](https://github.com/LuanRT/YouTube.js/blob/v16.0.1/src/core/Session.ts#L386-L399) · [Startup requests](https://github.com/LuanRT/YouTube.js/blob/v16.0.1/src/core/Session.ts#L449-L494)

Treat update delivery and API access as separate decisions. A working transport does not establish permission to use an upstream API: review the [YouTube Terms of Service](https://www.youtube.com/t/terms) and the Play policy before shipping. The lower-risk architecture is to keep WebView updates limited to the web UI and client logic, keep existing backend calls behind a stable API contract, and ship native changes through the appropriate app release channel.
