# ytify and Invidious audio URL research — 2026-11-25

ytify selects a URL from Invidious's video API; it does not generate a YouTube media URL in that client path. In the upstream Invidious revision reviewed here, Companion obtains the YouTube player response and resolves format URLs when needed. Invidious serializes those URLs for the client. Which server fetches the audio bytes is a separate question from which server resolved the URL.

## Verified in upstream source

1. **ytify requests and selects a format.** On a cache miss, its [stream resolver][ytify-resolver] tries the saved instance, then a shuffled list of Invidious instances sequentially, calling `GET /api/v1/videos/{id}` without `local=true`. It checks `adaptiveFormats` for audio, caches the response, and remembers the serving instance. The [player][ytify-player] filters audio formats, sorts them by bitrate, selects a preferred stream, and assigns its URL to the audio element. Its proxy helper swaps the origin only for Topic-author audio without a video element, a saved instance must exist, and URLs marked `&fallback` are excluded. After the instance attempts, ytify's resolver also tries the same-origin `/{id[0]}/{id.slice(1)}` fallback. That proves the client attempts the route, not what serves the deployed route or how it resolves URLs.
2. **Invidious calls Companion on the server.** The [video API handler][iv-api] calls `get_video`; the [video model][iv-video] can use cached data or fetch through the [video parser][iv-parser]. The parser calls [`YoutubeAPI.player`][iv-yt], which posts to `/youtubei/v1/player` at the configured private Companion URL with an operator-configured bearer key. Without Companion data the reviewed fresh-fetch path reports that Companion is not available. The browser does not send this key or call the private API.
3. **Companion obtains YouTube's formats.** Its [player route][ic-route] validates the video ID and calls its [player parser][ic-parser]. The [default request implementation][ic-req] uses YouTube.js to call the InnerTube player, passing the session's signature timestamp and the content PO-token value supplied by its token minter. It uses WEB by default, TV with OAuth enabled, and has a conditional client fallback when the first adaptive format lacks a URL. The parser invokes YouTube.js's format `decipher` on non-iOS/non-Android responses according to the response client marker, fills `url` and removes `signatureCipher` for those formats, then returns `streamingData` among other player fields. This is not the public YouTube Data API, and the client selection is behavior of this source revision, not a promise about deployed instances.
4. **Invidious exposes format URLs; rewriting changes delivery, not extraction.** The [parser][iv-parser] carries `streamingData` through, and the [JSON serializer][iv-json] maps `mimeType` to `type` and emits fields including `url`, `itag`, and `bitrate` when present. Without `local=1` or `local=true`, the API emits the format URL as stored. With either flag, it uses the [proxy URL helper][iv-url] to build an Invidious-origin URL retaining the original upstream hostname in `host`. The built-in Invidious [`/videoplayback` route][iv-media] uses that query value or derives a host when absent. Companion has its own [`/videoplayback` route][ic-media]; it expects a `host` and checks expiry, and handles range requests. The public API's `local=true` rewrite is not evidence that Companion proxies the bytes.

## Instance discovery and updates

ytify shuffles a hardcoded list when the resolver module loads. Remembering the last successful provider changes the first attempt, not list membership. There is no directory lookup or periodic refresh in the [resolver][ytify-resolver]. The history shows source edits: [`bd014b9b`](https://github.com/n-ce/ytify/commit/bd014b9b0b6cc9e17437247a75039a994590e88a) added `eu.yt.chocolatemoo53.com` and `invi.susurrando.com`; [`66abe46e`](https://github.com/n-ce/ytify/commit/66abe46e29f9cc48d0c4df98a2a54c857d0d1493) removed `invi.susurrando.com` and kept the EU host. Those diffs show what shipped in source, not why a host changed or where maintainers found it.

The [official Invidious directory](https://docs.invidious.io/instances/) publishes a curated list, an uptime dashboard, and a link to its [Instances API](https://api.invidious.io/). Those are external discovery sources, not inputs used by either playback resolver reviewed here. Directory inclusion does not guarantee client-compatible API or media requests; the directory itself marks some instances as requiring anti-bot challenges.

## What this checkout does

- [M14U's resolver](../src/lib/modules/getStreamData.ts) requests `/api/v1/videos/{id}?fields=adaptiveFormats,title`, without `local=true`, and attaches `streamProxy` to the response. Web starts there; Android first races bundled NewPipe extraction against the optional live resolver, falling back to Invidious if neither returns usable audio within the deadline. The first Invidious attempt uses `VITE_INVIDIOUS_URL`, saved state, or the first built-in host, in that order. Normal play can race the remaining defaults after failure; prefetch does not. This path has a five-minute cache and no ytify-style same-origin emergency fallback.
- The [player store](../src/stores/playerStore.ts) filters usable `audio/` formats, selects a preferred format, and calls [`proxyHandler`](../src/lib/utils/helpers.ts). For Invidious results it swaps the URL origin to `streamProxy` regardless of author. Without `streamProxy` it leaves the URL unchanged. It passes the resulting URL to native playback on Android or assigns `audio.src` on web.
- M14U's origin replacement is **not equivalent** to requesting an Invidious `local=true` URL: it does not add the original `host` parameter and can replace an already valid provider-supplied media origin. This matters if an instance uses a separate media hostname, expects explicit host information, or does not serve the returned path itself. It is a code-level compatibility risk, not evidence that any particular instance is misconfigured.

## Not verified for live instances

The host list, `adaptiveFormats` shape, and `googlevideo.com` or Invidious-looking media URLs do not identify the deployed resolver, proxy topology, or egress. A public instance could run a different version, patch, or routing configuration. No public instance, ytify fallback deployment, or Android device was tested for this source review. For an operator-controlled candidate, check the API response and the actual selected media request separately, including the final origin, browser playback and byte-range seeking. Compare the returned URL, the URL M14U currently builds, and the API's `local=true` URL; redact signed query strings in any logs. See [the provider review](invidious-provider-review.md) for deployment context.
