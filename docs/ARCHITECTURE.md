# Architecture

M14U separates **catalog metadata**, **stream resolution**, and **audio playback**. Web and Android share the same UI and client state. The Cloudflare Worker returns metadata, not audio bytes.

## UI and state

[`main.tsx`](../src/main.tsx) initializes the player store and console API before mounting React with `BrowserRouter`. [`App.tsx`](../src/App.tsx) declares the routes. [`AppShell`](../src/components/layout/AppShell.tsx) renders Home, Search, and Favorites; Now Playing and Queue are routed pages.

- [`playerStore.ts`](../src/stores/playerStore.ts) coordinates the queue, stream resolution, playback commands, history, and favorites. It persists selected state in `localStorage`.
- [`uiStore.ts`](../src/stores/uiStore.ts) owns UI preferences and panel state. [`src/lib/stores/`](../src/lib/stores/) contains the search and catalog-list stores.
- [`saavnFallback.ts`](../src/services/saavnFallback.ts) (`useSaavnFallbackStore`) owns Android YouTube-to-JioSaavn fallback state, outage mode, single-flight recovery probing, and persisted opt-out (`m14u-android-saavn-fallback`), rendered in `AppShell` by [`AndroidFallbackNotice.tsx`](../src/components/player/AndroidFallbackNotice.tsx) and controlled via `m14u.fallback.*` ([console API](CONSOLE-API.md)).
- [`lyrics.ts`](../src/services/lyrics.ts) fetches lyrics separately from LRCLIB.
- [`listenAlongStore.ts`](../src/stores/listenAlongStore.ts) is a “Coming Soon” stub. The presence of UI components or a Firebase service-worker file does not mean rooms or sync are active.

## Catalog metadata

The website defaults to JioSaavn. [`catalogStore.ts`](../src/stores/catalogStore.ts) stores the user's choice in browser local storage. First-run listening setup offers the web catalog choice without resetting an existing selection; later, use Settings in the desktop sidebar or the Home header on mobile. Switching catalogs does not change routes. It cancels pending search and suggestion requests and filters Home history and Favorites without deleting saved tracks. The queue and active playback stay intact. Tracks without a `jiosaavn:` ID remain visible on the Open Audio side, including legacy YouTube tracks. Android bypasses the website catalog setting and explicitly requests the Worker’s YouTube search and suggestions (`catalog=youtube`) by default; when `useSaavnFallbackStore` opens its F3 outage circuit (`mode === 'jiosaavn-fallback'` while `enabled`), [`search.ts`](../src/lib/stores/search.ts) routes Android search and suggestions to `searchJioSaavn(..., { allowNative: true })` and triggers lazy `maybeProbeRecovery()` until YouTube playback recovers.

[`listeningPreferences.ts`](../src/stores/listeningPreferences.ts) persists the listening language and first-run completion in the browser or app WebView. This is separate from UI locale. Search boosts explicitly tagged tracks within small relevance bands, keeping exact title matches and non-song results in place. JioSaavn exposes a song language; the current YouTube search renderers and Open Audio adapters do not supply reliable track-language metadata, so untagged results retain their relative order. A preference change cancels and refreshes the current search without touching the queue or history.

In default `MUSIC_CATALOG=open` mode, the Worker merges unfiltered/song search from Audius, Openverse's Jamendo music index, and Free To Use. It filters by license and available audio metadata. `/api/stream?id=…` resolves a source-qualified track ID to details and a direct audio URL, including saved Internet Archive and Commons tracks. The player uses that URL without contacting YouTube or Invidious for those tracks. Other catalog routes and saved YouTube tracks retain their existing behavior.

The client calls `/api/*` under `VITE_API_URL` when set, or uses relative URLs. [`vite.config.ts`](../vite.config.ts) mounts [`localAdapter.ts`](../src/backend/localAdapter.ts) for Vite development. The production API entry point configured in [`wrangler.toml`](../wrangler.toml) is [`worker.ts`](../src/backend/worker.ts).

Browser JioSaavn search tries Vercel first and retries on Render on failure. Searches also check YouTube Music in parallel without delaying primary results. A likely title match gets a targeted JioSaavn lookup before being reported as missing. `/api/up-next?id=…` provides up to twelve YouTube Music recommendations; the client shows only title-and-artist matches from JioSaavn. If none match, it searches JioSaavn for other tracks credited to the artist. Discovery failures leave the primary results intact.

Both API entry points use handlers in [`src/backend/`](../src/backend/). Those handlers query YouTube through `youtubei.js`/Innertube and normalize responses into app types. The Worker exposes search, suggestions, album, artist, channel, gallery, playlist, similar, and subfeed handlers. A handler’s presence does not imply a dedicated screen for it.

## From track selection to playback

On web, selecting an Audius or Openverse–Jamendo song from Home or Search starts it immediately and requests `/api/open-recommendations?id=…`. The Worker ranks remix relationships, same-artist tracks, and shared tags using the existing catalog eligibility checks. Up to five results append to the same queue without moving manually queued tracks. If none can be added, the player falls back to Audius and Jamendo tracks from the same browsing list. Play All, unsupported seeds, and Android retain their existing queue behavior.

For JioSaavn web selections, `/api/saavn-recommendations` returns up to eight distinct catalog tracks per batch. The player requests another batch from the current track when three or fewer tracks remain, at most once per active row, and appends without reordering the queue. The Worker excludes recent picks before matching discovery candidates; the player also deduplicates across the session. Clearing or replacing the queue or switching catalogs cancels refills.

When building a web queue directly from a list (such as Play All), the player applies the same title-and-artist identity to JioSaavn entries, since compilation copies can have different IDs. It keeps the selected release and preserves the order of the remaining tracks before any shuffle. Manual queue additions and saved queues are not rewritten.

1. The player store takes a track’s video ID and asks [`getStreamData.ts`](../src/lib/modules/getStreamData.ts) for playable formats. This module caches successful resolutions in memory for up to five minutes (bounded by provider URL `expire - 30s`, or a 1-minute fallback on native JS when expiry is absent).
2. Open track IDs resolve through the Worker. `jiosaavn:` IDs resolve to Render's `/api/audio/:id` relay on web regardless of the selected catalog; [`jiosaavn.ts`](../src/services/jiosaavn.ts) blocks `isNative()` calls by default unless `{ allowNative: true }` is explicitly passed (`getStreamData.ts` enables this on Android only when `useSaavnFallbackStore.getState().enabled` is true for F1/F3 fallback playback). For YouTube tracks, Android defaults to JS-first extraction (`Server JS` via `resolver/core` + `capacitorTransport`, racing optional v1 `liveResolver`) and falls back to `StreamExtractor` (`NewPipe`) and then Invidious; the browser starts with Invidious. The first Invidious attempt uses `VITE_INVIDIOUS_URL`, the saved provider, or the first default, in that order. Normal playback can try the remaining defaults; prefetch skips that fallback pool.
3. Web plays through `HTMLAudioElement`. Android passes the stream, queue, and `resolverKey` metadata to Media3/ExoPlayer through `NativePlayback` v2 while [`lookahead.ts`](../src/lib/modules/resolver/lookahead.ts) pre-resolves upcoming rows via `setResolvedSources`, and `PlaybackService` resolves unprimed or expired items on the native loader thread (using `ResolverEngine`/fallbacks for YouTube and `resolveJioSaavnAndOpen` against `JIOSAAVN_AUDIO_ORIGIN` for `jiosaavn:`). The Worker does not relay audio; Render relays JioSaavn audio with byte-range support. A provider returning formats does not prove the media URL will load or seek successfully.
4. Browser audio events or Android playback snapshots update React. On Android, React manages the app queue and sends commands, but the native service owns actual playback and system media controls. Changes to queue or transport behavior need verification on both platforms.

See [Android](CAPACITOR.md) for the bridge and service, and [setup](SETUP.md) for build and hosting configuration. The [provider review](invidious-provider-review.md) is a point-in-time investigation, not a list of guaranteed working hosts.

## Android playback v2 architecture and contracts

Pages owns the UI, catalog selection policy, foreground resolver code, and bounded lookahead. Native owns trust roots, network enforcement, headless resolver execution in the service, offline bootstrap, and Media3 playback and lifecycle. The catalog Worker remains a metadata API, `AppUpdater` remains the stable-release APK update path, and bundled `NewPipe` remains only as a transitional fallback while v2 soaks.

### Foreground transport

[`src/lib/modules/resolver/core.ts`](../src/lib/modules/resolver/core.ts) uses `youtubei.js/web` with a primary `VISIONOS` Innertube client fast path (30-minute per-`fetch` `visitorData` cache) and lazy-loaded `Player` + QuickJS WASM (`quickjs-emscripten-core` / `@jitl/quickjs-wasmfile-release-sync`) fallback across `TV`, `TV_EMBEDDED`, and `MWEB`. It validates 11-character IDs, suppresses `youtubei.js` logs (`Log.Level.NONE`), and filters out non-HTTPS, non-`.googlevideo.com`, `sabr=1`, and `enhanced_except_` URLs.

[`src/lib/modules/resolver/capacitorTransport.ts`](../src/lib/modules/resolver/capacitorTransport.ts) leaves global `fetch` and `XMLHttpRequest` patching disabled and calls `CapacitorHttp.request` explicitly via `createCapacitorFetch` / `capacitorFetch`. It enforces HTTPS-only YouTube metadata hosts (`www.youtube.com`, `m.youtube.com`, `youtubei.googleapis.com`, `youtubei.youtube.com`), allowlisted safe headers, request/response size bounds (`64 KiB` / `4 MiB`), same-origin redirect handling (max 3), concurrency cap (`4`), abort/5.5s timeouts, and isolated QuickJS WASM `evaluatePlayerScript` (`16 MiB` memory, `512 KiB` stack, `150 ms` deadline) with no bridge access or injected cookies/credentials. [`getStreamData.ts`](../src/lib/modules/getStreamData.ts) gates JS-first extraction on `VITE_YOUTUBE_JS_RESOLVER !== 'false'` and races `Server JS` against optional v1 `liveResolver` under a `6500 ms` deadline before `StreamExtractor` (`NewPipe`) and Invidious fallbacks.

### Native queue bridge

- On Android, [`src/lib/utils/platform.ts`](../src/lib/utils/platform.ts) checks platform/plugin availability and caches `NativePlayback.getCapabilities()`, which returns `abiVersion` (`2`), `sourceRefresh` (`true`), `localMedia` (`false`), `headlessResolver` (API 26+ & `JavaScriptSandbox.isSupported()` & configured keys/manifest), optional `sandboxSupported`, optional `saavnUnprimed` (`PlaybackService.isSaavnUnprimedSupported()`), and `resolverAbi` (`androidx-js-1`). Absence or rejection falls back to v1 defaults (`saavnUnprimed: false`), never web playback; ordinary playback errors do not trigger an ABI downgrade.
- Preserves v1 `loadQueue`, `updateQueue`, `control`, `getState`, and the `state` event, including seconds for position, duration, and seek, `sleep = -1` for end of track, legacy `url`/`proxy` compatibility, and `StreamExtractor` bitrate types (`number` in `getStreamUrl`, `string` in `getStreamData.adaptiveFormats`).
- A v2 `NativeQueueItem` retains `queueId`, `id`, `title`, `artist`, and `artwork`, and adds typed `resolverKey` (`provider`, `trackId`) plus optional `source` (`url`, `mimeType`, allowlisted `headers`, `expiresAtMs`). Neither executable scripts nor arbitrary relay endpoints are accepted. `queueId` identifies each row even when track IDs repeat; unresolved v2 rows map to `m14u-resolve://track/<queueId>`, while legacy v1 rows still map to `m14u-track://youtube/<id>`. `PlaybackSourceRegistry.kt` validates `jiosaavn` `resolverKey.trackId` (`[A-Za-z0-9_-]{1,64}`, accepting `jiosaavn:<id>` or `<id>`), and `NativePlaybackPlugin.kt` permits `resolverKey.provider == "jiosaavn"` without a pre-resolved `source`.
- V2 `loadQueue` and `updateQueue` carry `generation` (echoed additively in `NativePlaybackState`), and `setResolvedSources({ generation, entries })` updates [`PlaybackSourceRegistry.kt`](../android/app/src/main/java/dev/m14u/app/PlaybackSourceRegistry.kt) on the main looper without replacing `ExoPlayer` `MediaItem`s or disturbing the active buffer. The registry validates HTTPS public-address URLs (blocking private/loopback/link-local IPs, userinfo, non-443 ports), allowlisted headers, `queueId` + `generation` + `resolverKey` matching, expiry pruning (5-minute default TTL), bounded capacity (`1000` queue items, `256` cached sources, `128` batch entries), and 1 retry per load. Bridge mutations in [`playerStore.ts`](../src/stores/playerStore.ts) are serialized, and stale snapshots/results after Clear, reorder, selection, or native transitions are discarded.

### Resolution and lookahead

[`playerStore.ts`](../src/stores/playerStore.ts) resolves the active row once, sends its `source` in `loadQueue`, and schedules [`lookahead.ts`](../src/lib/modules/resolver/lookahead.ts) (`DEFAULT_LOOKAHEAD_COUNT = 2`) to pre-resolve up to two upcoming rows (accounting for `repeatMode` `'off' | 'all' | 'one'`, `EXPIRY_SAFETY_MARGIN_MS = 30_000`, `MAX_SOURCE_TTL_MS = 5 * 60_000`, `UNKNOWN_EXPIRY_TTL_MS = 4 * 60_000`, `LOOKAHEAD_FRESH_MARGIN_MS = 45_000`, and `resolveRowTrackId` for F1-remapped rows and `jiosaavn:` priming on older APKs) and push updates via `setResolvedSources`. On `visibilitychange`, `playerStore.ts` re-reads `NativePlayback.getState()` and re-primes lookahead without calling `loadQueue` over active native playback.

On Media3’s loader thread (`PlaybackResolvingDataSource` in [`PlaybackService.kt`](../android/app/src/main/java/dev/m14u/app/PlaybackService.kt)), loads first check `PlaybackSourceRegistry` for a valid `source` (clearing `DefaultHttpDataSource` properties on every open/close and preserving `DataSpec` byte position/range; invalidating and permitting at most one bounded retry on open failure via `TerminalPlaybackIOException` and custom `DefaultLoadErrorHandlingPolicy`). When missing or expired and `resolverKey.provider == "jiosaavn"`, `resolveJioSaavnAndOpen` validates `BuildConfig.JIOSAAVN_AUDIO_ORIGIN` (`parseSaavnAudioOrigin`: HTTPS on port 443, public host, path `/`, no query/fragment/userinfo; configured in `android/app/build.gradle`, defaulting to `https://m14u-jiosaavn.onrender.com`), opens `${origin}/api/audio/<id>` directly, caches it in `PlaybackSourceRegistry` (`DEFAULT_TTL_MS`), and enforces the 1-retry budget without falling back to YouTube resolvers. Otherwise, it invokes `ResolverEngine` + `ResolverBundleRepository` (candidate then last-known-good, promoting only on successful `upstream.open()`), then falls back transitionally to `NewPipe` (`StreamExtractorPlugin`) and legacy `proxy`.

#### Guarded Android JioSaavn fallback (F1 and F3)

[`saavnFallback.ts`](../src/services/saavnFallback.ts) (`useSaavnFallbackStore`) adds resilient Android fallback playback while keeping [`jiosaavn.ts`](../src/services/jiosaavn.ts) blocked on `isNative()` unless `{ allowNative: true }` is explicitly passed (`saavnDiscovery.ts` exports shared text-normalization helpers):

- **F1 per-track fallback:** On Android `getStreamData` failure or a native open error at `position === 0` on an unstarted YouTube row, [`playerStore.ts`](../src/stores/playerStore.ts) calls `recordYouTubeFailure` and runs `resolveTrackFallback` at most once per `queueId`. `findConfidentSaavnMatch` searches `searchJioSaavn(..., { allowNative: true })` under an `8s` timeout and accepts a match only on normalized title equality (stripping benign YouTube tags and `Artist - Title` prefixes), symmetric qualifier sets (`live`, `remix`, `cover`, `instrumental`, `sped-up`/`nightcore`, `reverb`/`slowed`, `karaoke`, `acoustic`, `lofi`, `mashup`, `8d`), credible non-generic artist overlap, and `<= 15s` duration difference. On match, `playerStore.ts` reloads `NativePlayback.loadQueue` with a fresh `generation` and `resolverKey: { provider: 'jiosaavn', trackId }` while keeping `favorites` and queue `song.id` intact (`activeFailoverMatches` preserves effective identity across lookahead), dropping stale completions after `clearQueue` or newer selections.
- **F3 session circuit breaker and recovery probe:** `recordYouTubeFailure` switches `mode` to `'jiosaavn-fallback'` after 3 distinct YouTube `trackId`s fail within 5 minutes (ignoring aborts, offline errors, and duplicate retries). While open and `enabled` (persisted opt-out in `localStorage` under `m14u-android-saavn-fallback`), [`search.ts`](../src/lib/stores/search.ts) routes Android search and suggestions to `searchJioSaavn(..., { allowNative: true })` and triggers lazy `maybeProbeRecovery()`. Recovery probes (`maybeProbeRecovery` or manual `retryYouTube`) are single-flight, skip offline or `document.hidden` states, back off `3m -> 6m -> 10m`, validate `resolveYouTubeStreams` + a `6500ms` `.googlevideo.com` `Range: bytes=0-0` probe via `CapacitorHttp.request`, and restore `'youtube'` mode on success. [`AndroidFallbackNotice.tsx`](../src/components/player/AndroidFallbackNotice.tsx) renders the F1 match toast, F3 header outage banner (`Retry YouTube` and `YouTube only`), and restored toast, while `m14u.fallback.*` (`status`, `retryYouTube`, `setEnabled`, `reset`) exposes console inspection and control.

### Headless runtime and trust

[`ResolverEngine.kt`](../android/app/src/main/java/dev/m14u/app/ResolverEngine.kt) (`androidx-js-1`) runs `androidx.javascriptengine:javascriptengine` (`JavaScriptSandbox`) on API 26+ on a single dedicated executor (`m14u-resolver`), executing [`scripts/resolver-headless.ts`](../scripts/resolver-headless.ts) (`VISIONOS` primary + inlined QuickJS WASM `Player.create` `TV`/`TV_EMBEDDED`/`MWEB` fallback) with a 64 MiB isolate heap, 512 KiB return limit, 12 s resolve timeout, and a restricted `ResolverHttpBroker` (`www.youtube.com` and `youtubei.googleapis.com` only, public DNS validation, no redirects, `MAX_RESPONSE = 4_500_000`, total cap `12_000_000`, allowlisted safe headers, no DOM/Capacitor bridge/credentials).

Keep v1 `resolver.json` and P-256 IEEE-P1363 signing intact for legacy foreground use. V2 uses fixed Pages paths `/resolvers/v2/manifest.json` (`no-store, no-cache`) and `/resolvers/v2/<version>/resolver.js` (`immutable`, max `3,000,000` bytes) configured in [`public/_headers`](../public/_headers). [`scripts/build-resolver.mjs`](../scripts/build-resolver.mjs) signs domain-separated canonical bytes (`m14u-resolver-v2\n<version>\nandroidx-js-1\n<keyId>\n<artifactPath>\n<byteLength>\n<sha256Hex>`). [`ResolverBundleRepository.kt`](../android/app/src/main/java/dev/m14u/app/ResolverBundleRepository.kt) pins HTTPS manifest URL and P-256 SPKI keys via `BuildConfig.RESOLVER_V2_PUBLIC_KEYS` / `RESOLVER_V2_MANIFEST_URL`, verifies manifest and artifact bytes before staging and on disk reads in `noBackupFilesDir/resolver-v2`, enforces a monotonic high-water version mark, refreshes asynchronously off the playback path (15-minute minimum interval with exponential backoff, no redirects), promotes candidates only after `upstream.open()` succeeds, and quarantines repeated faults (`>= 2`) back to the last-known-good bundle.

[`scripts/resolver-smoke.mjs`](../scripts/resolver-smoke.mjs) (`pnpm test:resolver:smoke` via [`scripts/resolver-smoke.test.mjs`](../scripts/resolver-smoke.test.mjs)) deterministically tests foreground `core.ts` + QuickJS WASM and compiles `scripts/resolver-headless.ts` (`< 3,000,000` bytes) to run inside bare `node:vm` HTTP isolates; [`build-apk.yml`](../.github/workflows/build-apk.yml) runs this gate on web checks, and [`youtubei-sync.yml`](../.github/workflows/youtubei-sync.yml) runs daily `youtubei.js` sync PRs (`sync-and-test`, plus advisory `--live` probing) and `main` v2 bundle signing (`sign-v2-bundle`, see [live resolver setup](LIVE-RESOLVER-SETUP.md)).

[`MainActivity.java`](../android/app/src/main/java/dev/m14u/app/MainActivity.java) (`OfflineBridgeWebViewClient` / `OfflineFallbackPolicy`) keeps the bridge scoped to the configured origin (`https://m14u.pages.dev` in production) and redirects main-frame network or `5xx` errors to `file:///android_asset/public/offline.html` ([`public/offline.html`](../public/offline.html)) with no Capacitor bridge, loop-safe same-origin retry, and history cleanup on recovery. Because local `file://` and remote HTTPS WebViews have separate storage origins, native `NativePlayback` snapshots remain authoritative for active playback.
